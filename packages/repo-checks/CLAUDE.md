# @app/repo-checks

The specs whose subject is the repo itself rather than any package: the pre-merge chain's graph and cache
keys, the recorded spec costs, the timeout budgets, where specs live, and the scripts under `scripts/` that
the other checks run.

Nothing here is published, imported by the app, or part of a pack. It is a workspace because a spec needs
a package to live in — and because which package it lives in decides whether `npm run spec` can find it.

## Why it exists

These specs used to live in `packages/abuddy-cli/tests/build/`. Not because they were about the CLI —
none of them is — but because it was the package with a vitest config nearest the scripts. Two costs came
of that:

- **They were unreachable from what they check.** `npm run spec` asks which package a changed file belongs
  to, and a change under `scripts/` belongs to none, so it reported "nothing changed inside a package" and
  ran nothing. The repo's own tooling was the one part of the tree its own command could not check.
- **They were 9.2s of a suite meant to be a per-change loop.** `@abuddy/cli`'s fast half is the loop its
  contributors run; a sixth of it was answering questions about the chain.

`scripts/spec.ts` now routes `scripts/` and any `vitest.config.ts` here, and
`tests/repo-check-boundary.spec.ts` holds the other half: a spec that reads the repo's scripts belongs in
this package, and this package holds nothing else — bar the layout checks its `LAYOUT_CHECKS` names, which
read the tree and so have no `scripts/` module to import.

**The two halves ask different questions, and that is what keeps the lists empty.** The first is about
*reachability* — `scripts/spec.ts` routes a change under `scripts/` here and nowhere else, so a spec
importing one from another package will not run when what it covers changes — and it asks only about
imports, since only an import can create that. The second is about *cohesion*, and asks the wider question,
because a spec that spawns `scripts/with-source.mjs` is as much about repo tooling as one that imports it.
Asking one question for both cost an allowlist: `package-freshness` names a script path as an expected value
and tripped the reachability check it cannot affect. `check:specifiers` now refuses a package reaching into
`scripts/` at all, so the first check should stay empty by construction.

The same shape has since turned up twice more, which is why `tests/spec-placement.spec.ts` generalises it:
`@abuddy/testing` and `@abuddy/ui` had no suite at all and their specs lived in `@abuddy/cli`. Every package
extraction this repo has done left tests behind, and nothing noticed any of them until someone went
looking.

## Tests

Two halves, split by measured cost exactly as every other suite is — the rule and the band are in
`scripts/lib/spec-cost.ts`, and `etc/spec-cost.json` is this suite's record.

- **`npm test -w @app/repo-checks`** — the fast half (`tests/**/*.spec.ts`): 20 specs, about 3.5s of file
  time.
- **`npm run test:integration -w @app/repo-checks`** — the expensive half
  (`tests/**/*.integration.spec.ts`): 3 specs, about 9.8s. Each runs a compiler over a fixture tree.

Both run in the chain: the fast half inside `test:unit:host` (this is a host suite — it resolves workspace
`@abuddy/*` source through the `@abuddy/source` condition), the expensive half in `test:integration`, which
names every workspace that has a second config.

## What is here

| Spec | Subject |
|---|---|
| `chain-graph`, `chain-schedule`, `step-timing` | the chain's run order, the scheduler that admits its steps on a core budget, and what a step costs. Also that no step has outgrown the rung it declares — a **bound** on a declared cost, never a way of choosing a class from one, which is the distinction `goal-measured-placement.md` draws as *"a bound is not a fit"*. Its fraction is derived rather than picked, and **per rung**: each one declares how much its kind of work stretches on a smaller box, so `declaredShare` is where a cost lands on the machine *that* rung is sized for and 1 is exactly on the deadline. Two of the three borrow the measured figure and say so, which is what the provenance case holds — exactly one of `measured` and `until` per rung, so a measured row cannot keep a stale condition and an assumed one cannot omit the terms. Still the loosest useful bound and a creep detector rather than a finder: the two genuinely tight steps were found by reading the table, `packages:ensure` and `compile` at 93% and 87% four times slower, moved out of `quick` because a step that builds is a bundle. It also holds the one report in the repo whose subject is a deadline — what a step says when its class killed it. A kill truncates the measurement, so what it proves is the *rope*, the deadline over what the step costs healthy, and the conclusion drawn from it is machine-dependent: "wedged" where the costs were measured, and anywhere else the rung's own factor with the rope named as the finding, since on a smaller box a step can overrun by being slow and that is the evidence the two borrowed rows are waiting for. And an inventory of the rungs a *direct* `npm run` reaches through `scripts/bounded.ts`, which is the second path into the ladder and the one a reachability claim forgets: a rung's `until` said nothing reached `scenario` while two CI steps bound at it that way. It fails on a change rather than a hit, so the prose describing how a rung gets exercised is re-read when the set moves, and the scan is mutated in the spec because one that matched nothing would satisfy every assertion over it |
| `core-budget` | what each step takes of the machine, which is what the chain admits on (`--cores`, defaulting to this machine's cores). Two subjects: `coresFor`'s arithmetic, asked about a ten-core box from whatever box it runs on, and the direction `chain-table` cannot ask — every worker cap declared in any of the repo's seventeen vitest configs has to be a width `POOL_WIDTH` knows, so a new pool cannot take the box while the chain goes on weighing it at one core. The scan is mutated in the spec, because the prose in `vitest.integration.config.ts` names `maxThreads` three times without declaring it |
| `record-seconds` | `chain --all --record`, the update half `seconds` never had — and `--adopt`, which rewrites `MEASURED_ON` with the costs, because a table and the box it was measured on are one fact and nothing wrote the second. Its locator is its own rather than a shape added to the numeric splicer, whose every span is digits and whose safety is re-reading them; the cases hold it to finding exactly one declaration and refusing anything else. A sample cannot re-derive itself, so `driftReport` is its check and this is its write; what the cases hold is the write into source, since a rewriter wrong about a span corrupts a file rather than failing one. They run against sources passed in, so they rewrite nothing. The span re-read has no case on purpose and says which edit would give it one |
| `sweep-forget` | that one shared reading of the tree stays honest across a run, which is what lets the chain's dispatch decisions share one — 1715ms read per step against 189ms shared, on 28 steps. A sweep answers as of its first look, so each step's declared writes are forgotten as it finishes. The cases use a real stamp over a real tree, because without one every answer is "no stamp" and comparing that to itself passes whatever `forget` does. It found the bug it now guards: the three memos are not keyed alike — `walked` on the absolute target, `seen` and `digests` on repo-relative paths — so clearing one space re-walked the directory and then answered from bytes read before it moved. Also holds the one declaration the sharing rests on that is not definitional: a reader of a transient write is kept apart by a mutex, not by an edge |
| `chain-stamps` | that the stamp store holds a record for each cached step and nothing else. A stamp for a step declaring `neverCachedBecause` is a bug, not litter — it is how the chain skips work a step promised always to do, which is the failure `packages:ensure` is uncached because of. A stamp for a step that is no longer in the table is a record with no subject, and this store grew one when `typecheck` became eighteen steps; `pruneStamps` clears both on every run. Evidence-dependent: a checkout that has never run the chain has no store, and the first case says so rather than passing over an empty directory |
| `typecheck-legs` | that a leg's declared `scope` is no narrower than the workspaces its script names. The scope is a cache key, so it is declared rather than parsed out of the shell: a wrong parse gives a wrong key silently, where a wrong declaration fails here. One direction only — wider costs cache hits, narrower is a leg that does not re-run when what it compiles changes |
| `dep-files` | what the compiler reports it read (`tsBuildInfoFile`, one per typecheck leg), against what `typecheck` declares. The only input check here that compares a declaration to an *observation* rather than to another declaration, which is why it is the one that can catch a read nobody modelled — the affordable stand-in for a sandbox that would refuse the read outright. Also holds the dep file to itself, since it is a proxy and records what was read *last* time: a file written by another compiler, or under other options, is refused by cause. Two gotchas it encodes, both found by running it — the paths are lowercased on a case-insensitive filesystem, and 8401 of the recorded reads sit in a nested `node_modules`. It also holds the prune that keeps its tracing case about something: nothing removed a dep file when its tsconfig went, so deleting a workspace left one answering for nobody and the step stayed red on litter until a file was deleted by hand — `npm run typecheck` now clears those before its legs run, and what the tracing case is left with is the cause a prune cannot fix, a dep file written by something other than a declared leg. The prune's own cases run over a directory of their own, since pruning the real cache would delete the evidence every other case here reads. It also holds the other tool this repo can ask: `abuddy build` records each bundling phase's module graph (`.abuddy/reads.json`, read by `scripts/lib/build-reads.ts`), which is what observes `compile` and `test:external-pack:contract` — the two steps that had no per-step evidence at all. The phase set is asserted as well as the reads, because a dropped capture makes the recorded set *smaller* and a reads-are-declared gate cannot see that by construction. Both steps stay on the list of what nothing verifies per-step, since what is observed is the bundling and not the codegen, seed compilation or pack rules around it |
| `chain-inputs` | every step's cache key covers what the step reads: that the declared inputs reach the whole tracked tree, that a gitignored input belongs to whoever writes it, that a step reading another's output depends on that step, and that a build unit declares the modules its build script imports. It also holds the two rules about what a fingerprint leaves out — that no `CLAUDE.md` is in one, except the single guide a spec asserts the text of, and that a suite holding a guard over the whole repo declares the whole repo, which is how `identity-guard` came to miss a violation in a package that was not its own |
| `chain-table` | the step table's own shape, answered without opening a file: that a pool declares what its projects declare, that a step keeping a cache of its own says so with `forceArgs`, that a recorded artifact has both a `check` and an `update`, that every flag the chain accepts is named in the guide (which `--cores`, `--record` and `--force` all once were not), and that the two root vitest configs' project lists match what they are derived from. Those two are read **as vitest resolves them**, not as a regular expression reads the file: the unit one anchored its pattern to a line start and so happened to skip a commented-out project, and the integration one, written from it later, did not — commenting a project out dropped five specs from the chain with every case green. It also holds the pooled run to the width it documents, in both directions: the cap at the root, where `poolOptions` is read, and no inert per-package copy, which would read as protection while doing nothing. And it holds `ci.yml`'s header to `ASSUMED_RUNGS`: that list is derived from the table and so is always right, but nothing held the prose to it and six places restate which rungs are a borrow — one of them named the wrong count within a day, which took eight paths to correct and was missed in a ninth. The header is the restatement that earns a check rather than review: it is the only one outside source, so no reader of the code passes it, and it is what a person reads when deciding whether to switch the triggers on. It reads the comment block above `jobs:` and not the file, since every rung appears in some `run:` line, and the first version of that read returned an empty string and passed over nothing. Split from `chain-inputs` in 2026-10, when that file's walks crossed the cost threshold and the two subjects turned out to be independent |
| `fingerprint-scope` | what a step's cache key leaves out, and what a suite has to declare because of what its specs read. Two rules: no `CLAUDE.md` is in any cache key, so a prose edit runs nothing — except the one guide a spec asserts the text of, which is a real input and is listed rather than skipped; and a suite holding a guard whose subject is the whole repo declares the whole repo, taken from the specs' own AST rather than a list. The second rule exists because `identity-guard` lived in `@abuddy/sdk`, whose project is re-run only when that package moves, and so missed a banned path committed to `@abuddy/cli` through two green chain runs |
| `suite-reads` | that a suite declares the files its specs load. `chain-inputs` asks the coverage question — every tracked file is *some* step's input — which leaves the per-suite one unasked, and three defects in one week were that gap. A suite's project is re-run when **its** inputs move, so a spec importing a file nobody declared keeps its last result while that file changes: measured, touching `abuddy-ui/src/tailwind-preset.ts` left `@abuddy/cli`'s project not stale while the spec that imports it sat there. Relative imports only, which is what the graph follows — a bare `@abuddy/…` is covered by the manifest instead, so this compares a graph against two declarations rather than against an observation, and a path built at runtime it cannot see at all. One direction: over-declaration is not a finding, because `suiteInputs` declares whole directories and most files under them are legitimately never loaded. Both sides of the step case expand declared paths through one memoised reading, because in a chain run another lane writes into the fixture packs' `dist` while this one walks: taken twice, the two sides described two trees and the case reported a step as under-declaring over a difference that was only the clock |
| `chain-output` | how a chain run puts a step on a line, and what it concludes from a re-run: a step that timed out again alone is "wedged, not crowded" only on the machine the deadlines were sized against — running alone rules out contention wherever it runs, where "wedged" needs the deadline to be generous here, so off that machine it claims the half the retry established and no more. Also: a reason too long for its row is indented to the column it starts at rather than wrapping to column 0, where it reads as another step; every row's columns are composed from one name width and asserted against the **widest declared step name**, since the version that composed them from `'x'` held while three row shapes were a column out for the one step wider than the column. A cached step keeps its own line where it was skipped, and a suite's slowest tests sit in that step's own time column. And what it prints under a step that passed and is stale again: the inputs that differ from the digests its stamp recorded, each with what happened to it and whether it moved while the step ran or since, a declared-set change instead of a file list because for that cause there are none, and the file whose mtime moved while its bytes did not — named, because a count is not something anyone can act on, and the report used to call that file a cause because it walked mtimes rather than asking the fingerprint |
| `suite-split`, `suite-timeouts`, `slow-tests` | the recorded spec costs, held as a **window** of up to `WINDOW` readings per spec whose median is the cost — so one reading is kept and cannot become the answer, while two that agree can. Its replay cases carry the two defects that bought it, from the readings that caused them: a contended run at 78% idle moved two specs across `INTEGRATION_ABOVE_MS` and the gate demanded two renames nobody had earned, and the band that absorbs jitter then stopped the clean readings correcting it, since displacing a value takes 35% of it. The tie rule is the part worth knowing — a two-reading window answers with the incumbent rather than the mean, because the pair disagrees by construction and averaging let one extreme reading carry the answer half its own distance, which across an edge is the first defect with an extra step. The fast-half budget goes through `priceSpecs` rather than a sum of its own, because that function already refuses to treat an unrecorded spec as zero — *"a total that quietly omits a file is a prediction that gets better the less it knows"* — and a missing cost used to make this one vouch for a half it had stopped counting, with an absent record passing it vacuously on a total of 0. Also including the two states that let a machine which is not the record's contribute to it: an entry may sit in `unmeasured` with no price, which is what makes the `unrecorded` finding satisfiable by anyone, and the record names the `machine` it was measured on so the placement cases scope on that rather than on the chain's `MEASURED_ON`, which describes a different record's box. The same two states are what a **busy** box writes, which is the third reason `writesMembershipOnly` answers for: it refused before, and the refusal blocked a landing on a gate that only wanted the spec listed. Also the per-size timeout budgets (`SIZE_MS`), and the slow-test report. `suite-split` also holds the two edges to agreeing with each other: a move changes the reading, so the band between them has to be wider than that change or a spec is told to move in both directions at once — which `spec-plan.spec.ts` was, until 2026-10-01. The property scans both directions over `halfFor` and counts the costs that took each branch, because a `halfFor` that moves nothing would otherwise pass over an empty scan |
| `decision-mutations` | whether a decision in `scripts/lib/` can be observed at all: each entry breaks one line of `spec-cost.ts`, `measure.ts`, `step-timeouts.ts`, `chain-schedule.ts` or `core-budget.ts`, imports the copy, and calls the same function on the same input as the real one — and the two answers must differ. What qualifies a module is reachability rather than subject: the mutant is written to a temp directory, so it must import nothing a `node_modules` walk-up would be needed for, which is why `chain-output.ts` is absent. It replaced a hand-run ritual with three ways to lie — a `git checkout --` that restores the index rather than your work, a filtered run that reports nothing when it matched nothing, and a grep narrow enough to turn an error into silence — two of which were observed in one session. Two cases had already shipped that could not see what they covered, both found by breaking the source by hand, which left the evidence in a commit message and nowhere that runs again. The anchors are text, so each is asserted to match exactly once: without that a refactor turns an entry into a no-op that still passes. It pins a discriminating input per decision; it does not police whether the cases elsewhere use one. `step-timeouts.ts` had no case of any kind before it arrived here — `chain-graph` reaches three of its exports now, but a rung's *deadline* is still observed only from here — and `core-budget.ts`'s off-machine arms had none that passed a machine other than the one running, which is the only way those paths are reachable. One entry's mutation is the permissive answer rather than a crash, on purpose: `timeoutMsFor` dropping its guard would throw reading a field of `undefined`, which differs from the named error and so would pass while testing nothing the decision is about |
| `spec-waits` | that a spec waits for the thing it waits for rather than asserting how long it takes. Its mutation cases hold both: an unlisted sleep is reported and the one inside a string is not. Two lists, because six of the nine files holding one are nobody's current work and writing a reason for a spec nobody has examined is inheriting a justification — `BARE_WAIT_BY_DESIGN` carries a reason each, `NOT_CONVERTED_YET` carries the backlog and its count, named as `spec-placement`'s `NOT_MIRRORED_YET` is |

The population is what the pool *loads*, its specs plus what they import, so a support module's spawn is counted once where the call is rather than fanning out to importers that never make it, and a fast spec spawning into another pool's budget is left out. Counts are recorded beside the files because the cap is about how much spawning, not which files: a sixth call in a file already listed is the creep. Its mutation case drops a spawning file from the **input** and requires the answer to follow — where its predecessor's doctored the expectation, comparing three entries against two, and passed with the detector stubbed to return nothing |
| `measure` | what `npm run measure` decides: when a timing is refused, what a series says, how a number is quoted, what makes two failures the same failure, and what a clean run licenses you to claim (0 of 5 bounds the rate at 45%, 0 of 20 at 14%). It exists because five numbers in `goal-integration-pool` were wrong and three reached commit messages. Three cases carry the shape: a CPU sample that did not advance **throws** rather than reading as 0% idle, since the `top` parse it replaces returned 0% for a line it could not read and a gate waited for ever; `cpuTimes` counts a CPU state it has never heard of, because a hardcoded field list is a restated population; and a flag with no value is an error, which is what let `"cmd" --busy` run with no load and call the box 95% idle |
| `loop-blocks` | what `npm run measure:loop` decides about a run's event-loop blocks. A process's role is derived from the recorded **process tree** — a pool worker is the topmost process carrying a tinypool worker id — where matching the entry file by name would call every process `other` the day it is renamed. A block is the worse of two sources, because `monitorEventLoopDelay` records a gap only once the loop turns again: measured, a 4s spin then an exit read 0ms from it. And a factor is quoted only where it is a thing that could happen, since `5454.5x slower` on an 11ms block makes a reader discount the rest of the report |
| `bounded-spawn` | one case, for the thing that bites a person hours later: `--busy` starts processes that burn a core each, and stopping it has to stop them. It spawns a grandchild outliving its parent shell, because killing the child orphans the rest — the failure that left a `generate-entries` at 99% CPU for a day and a half. An earlier version of the burners carried its own signal handlers, which could never run, and three of three survived an interrupt |
| `repo-check-boundary`, `spec-placement` | where a spec belongs: this package's own boundary, that every package with source has a suite, that no spec reaches into another package's tree, and that an `.integration.spec.ts` suffix names a half its package actually has — the suffix is what `halfOfPath` reads, so in a package with one config it claims a placement nothing implements, and renaming a file into it silences the placement checks while the spec goes on running exactly where it was |

`tests/spec-plan.spec.ts` itself checks that this table names every spec here, in both directions. It had to:
that spec was added without a row, and ten cases were added to it before a review noticed. A table of eighteen
that lists seventeen is the same failure as an exception list with a stale entry, which this package already
checks in three other places.

## Conventions

- **Find the repo root with `REPO_ROOT`** (`@abuddy/host/build/packages-built`), never by counting `..`
  from `import.meta.dirname`. Two specs arrived here with a hard-coded depth and broke on the move; the
  exported one is derived from a marker file and cannot.
- **A spec that reads the built `@abuddy` packages** calls `packagesBuiltOrRefuse()` from that same module,
  which skips when they are not built and refuses when they are stale. The suite's `pretest` builds them;
  that call is what catches a run which bypassed it.
