## Background

- `@apack/ui` ships its `.vue` files as source (`dist/**/*.vue`), and each pack's Vite build compiles them and inlines the components into the pack's `fe.js` (`packages/apack-cli/src/build/fe-bundler.ts`). Only `@apack/sdk/fe` and the libraries in `SDK_FE_MODULES` / `SHARED_DEPS` (`packages/apack-host/src/build/shared-deps.ts`) come from the host through `window.__apack`, which the renderer's `virtual:host-deps` plugin builds (`packages/renderer/vite.config.ts`).
- Consequences of inlining:
  - Every pack that uses `TiptapEditor` or the Monaco editors ships its own copy of them and of lowlight.
  - Stateful UI modules (e.g. `components/monaco-config.ts`) get a separate instance per pack. The DSL type registry already had to move into `@apack/sdk/fe` for this reason.
  - Packs depend on their Vite and `@vitejs/plugin-vue` setup matching how our SFCs are written.
- The `.ts` specifier spike (`docs/archive/goals/goal-ts-import-specifiers.md`) failed only because of the shipped SFC source: `tsc` rewrote the SDK's and host's JS correctly, but copied `.vue` files kept `./x.ts` imports that don't exist in `dist/`.
- What other libraries do (published tarballs and build configs checked 2026-09-13):
  - 19 of 20 Vue component libraries publish compiled JS as the runtime: Reka UI (tsdown, `dts: { vue: true }`), Ark UI (Vite `preserveModules` + vite-plugin-dts), Element Plus (Rollup + plugin-vue, `preserveModules`), PrimeVue (Rollup), Vuetify, Naive UI, Ant Design Vue, Quasar, Headless UI, Vue Flow, Tiptap Vue 3. Nuxt UI ships `.vue` source, and only works with its own Nuxt/Vite plugin in the consumer's build.
  - Plugin hosts provide the UI kit at runtime. Grafana's plugin build marks `@grafana/ui`, `@grafana/runtime` and `@grafana/data` external by default (`bundleGrafanaUI: false` opts into bundling); `@grafana/ui` is compiled and uses a source export condition like ours. Directus shares `vue`, `vue-router`, `vue-i18n`, `pinia` and its SDK with extensions and registers its app components globally.
  - Reka UI's tsdown config avoids per-file ("unbundle") output for SFCs ("creates a lot of unwanted files because of the multiple sections of SFC files") and relies on shared chunks.

## Decisions

Final.

1. **`@apack/ui` publishes compiled JS.**
   - A Vue-aware bundler compiles SFCs and `.ts` modules into ESM. Phase 0 picks tsdown or Vite library mode with `preserveModules`. `vue`, `@apack/sdk` and every host-shared library are external.
   - Modules shared by several entries (e.g. `monaco-config`, the tiptap extensions) are emitted once, as a shared module or chunk, never duplicated per entry.
   - Declarations stay per module from vue-tsc (`X.d.vue.ts`). The explicit exports map stays generated by `scripts/exports.ts`, with every export keeping `types`, `@apack/source` and `default`.
   - Component exports drop `.vue`: `@apack/ui/design/button`, `@apack/ui/components/tiptap/TiptapEditor`. Their `@apack/source` target stays the `.vue` file, so the monorepo still needs no build step.
   - Component CSS (scoped styles, `tiptap-theme.css`) is emitted as CSS the compiled module imports, so a consumer's bundler collects it.
   - This amends `goal-ts-import-specifiers.md` Decision 1 for `@apack/ui` only: a Vue compiler decides its output. No script post-processes that output or rewrites specifiers. `@apack/sdk` and `@apack/host` stay `tsc`-only.
2. **The host provides `@apack/ui` to packs by default (the Grafana model).**
   - The renderer exposes every `@apack/ui` export on `window.__apack` (one namespace keyed by export subpath), next to the existing SDK modules.
   - The pack FE bundler turns every `@apack/ui/*` import into a proxy to the host's module, the way it handles `@apack/sdk/fe`. Component exports proxy their default export.
   - `apack.json` `fe.bundleUi: true` opts a pack into inlining all of `@apack/ui` instead. It's all or nothing, so a pack never mixes host and bundled instances of the same modules. The pack's Tailwind config then also scans `node_modules/@apack/ui/dist`.
   - Compatibility is the same contract as `@apack/sdk/fe`: packs declare `hostVersion`, and `@apack/ui`'s public API changes follow semver, checked by its API reports.
   - The host-registry guard keeps working for inlined modules (`fe.bundleUi`).
3. **`.ts` relative specifiers in `@apack/sdk`, `@apack/host` and `@apack/ui`, after Decisions 1–2 land.**
   - sdk and host: `allowImportingTsExtensions` + `rewriteRelativeImportExtensions`, emitted by `tsc` (validated by the spike).
   - ui: the bundler resolves `.ts` imports, and vue-tsc typechecks and emits declarations with `allowImportingTsExtensions` only. With the rewrite flag, vue-tsc reports TS2876 on `.vue` imports.
   - Consumers that compile this source get the flags the spike recorded: api `allowImportingTsExtensions` + `rewriteRelativeImportExtensions`; cli, testing, host, ui and the `facade-typing` test `allowImportingTsExtensions`; `scripts/bundle-package.ts` `--allowImportingTsExtensions`.
   - Declarations keep `.ts` specifiers (TypeScript doesn't rewrite them). The spike showed consumers resolve them under node16 and bundler, and the published consumer tests keep checking that.
   - Generated pack code (`generate-entries.ts`) keeps `.js`.
   - Not `erasableSyntaxOnly`.
4. **A guard rejects relative `.js` specifiers** in the three packages' `.ts` and `.vue` sources. Use oxlint's `import/extensions` rule if it can express "`.ts` required, `.js` rejected" for relative imports; otherwise a small test. The nodenext typecheck against extensionless imports stays.

### Implementation notes

- Decision 1's "their `@apack/source` target stays the `.vue` file" doesn't work for types: TypeScript ignores exports targets with a `.vue` extension, and vue-tsc only maps specifiers that end in `.vue`. It went unnoticed while a built `dist/` existed, because TypeScript fell back to its declarations; from a clean checkout the renderer and default-setup couldn't resolve `@apack/ui/design/ToastNotification`. Tsconfig `paths` to `.vue` files didn't help either. Each public component therefore has a `.ts` entry module (`design/button.ts` re-exporting `./button.vue`, like PrimeVue's per-component `index` modules), and the exports map lists `.ts` modules only. Component exports stay extensionless, and the monorepo still needs no build step.
