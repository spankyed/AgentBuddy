# Monaco DSL Defs: Staleness Audit

## Pipeline overview

Monaco editor intellisense for the action, prompt, and database DSLs flows through a multi-stage pipeline:

```
src/defs/{action,prompt,database}.ts          (1) Hand-authored type source
        ↓
src/__generated__/defs.config.mjs             (2) Generated manifest (from abuddy.json)
        ↓
rollup -c rollup-defs.config.mjs              (3) rollup-plugin-dts bundles each into a .d.ts
        ↓
dist/defs/monaco/{action,prompt,database}-defs.d.ts   (4) Bundled type declarations
        ↓
src/__generated__/dsl-register-fe.ts          (5) Generated, imports (4) as ?raw strings
        ↓
registerDslType() → Monaco TypeScript worker   (6) Runtime registration
```

### File roles

| Stage | File | Generated by | Purpose |
|-------|------|-------------|---------|
| 1 | `src/defs/action.ts` | Hand-authored | Exports the types/values available in action DSL (services, params, z, entity types) |
| 1 | `src/defs/prompt.ts` | Hand-authored | Exports prompt DSL types (usePrompt, params, PromptEntity) |
| 1 | `src/defs/database.ts` | Hand-authored | Exports EARS DSL types (qx, tx, bp, spawn, entity helpers) |
| 2 | `src/__generated__/defs.config.mjs` | `abuddy generate-entries` | Tells rollup which defs exist and their targets (monaco/authoring) |
| 3 | `rollup-defs.config.mjs` | Hand-authored | Rollup config — reads (2), uses `rollup-plugin-dts` with `tsconfig.defs.json` paths |
| 4 | `dist/defs/monaco/*-defs.d.ts` | `npm run generate:defs` (rollup) | Bundled `.d.ts` files wrapping types in `declare module "@app/defs/<name>"` |
| 5 | `src/__generated__/dsl-register-fe.ts` | `abuddy generate-entries` | Imports (4) as `?raw` and calls `registerDslType()` for each DSL |

### Dependencies of the def source files

The def source files (stage 1) import from other generated and SDK modules:

- **`action.ts`** imports `featureServices` from `@/__generated__/services` and types from `@/__generated__/types`
- **`prompt.ts`** imports types from `@/__generated__/types`
- **`database.ts`** imports from `@abuddy/sdk/ears` and `@abuddy/sdk/types`

These imports are resolved by `tsconfig.defs.json` paths, which maps `@abuddy/sdk/*` to monorepo source and `@/__generated__/*` to the pack's generated barrels.

## What triggers regeneration

| Trigger | Regenerates `defs.config.mjs` (stage 2)? | Regenerates `dist/defs/` (stage 4)? | Regenerates `dsl-register-fe.ts` (stage 5)? |
|---|---|---|---|
| `npm install` | Yes (prepare → `generate-entries`) | No | Yes (prepare → `generate-entries`) |
| `npm start` | Yes (prebuild:be → `generate-entries`) | No | Yes (prebuild:be → `generate-entries`) |
| `npm run start:gen` | Yes | Yes (`generate:defs`) | Yes |
| `npm run build-prod` (build.sh) | Yes | Yes (step 3.5) | Yes |
| Manual `npm run generate:defs -w @app/default-setup` | No | Yes | No |
| Branch switch | No | No | No |

**The gap:** `npm start` does NOT run `generate:defs`. The rollup step that produces `dist/defs/monaco/*.d.ts` only runs in `start:gen` and production builds. Regular `npm start` skips it entirely.

## Staleness scenarios

### 1. SDK type changes (low frequency, high impact)

If EARS types, service interfaces, or SDK exports change, the bundled `.d.ts` files in `dist/defs/` still contain the old type shapes. Monaco shows stale intellisense until `generate:defs` is run.

**Example:** Adding a new SDK export to `@abuddy/sdk/ears` that `database.ts` re-exports. The source file is updated, but `dist/defs/monaco/database-defs.d.ts` still has the old bundle.

### 2. Generated barrel changes (medium frequency, medium impact)

`action.ts` imports from `@/__generated__/services` and `@/__generated__/types`. When a feature's services or types change, `generate-entries` updates those barrels (now runs on every `npm start`). But `dist/defs/` still has the old rolled-up types.

**Example:** Adding a new service to a feature. `generate-entries` updates `services.ts` barrel, but `action-defs.d.ts` still exports the old `featureServices` shape.

### 3. Defs source changes (low frequency, high impact)

Directly editing `src/defs/action.ts` to add a new global or change a type. The file is saved, Vite sees the change (if the dev server is running), but `dist/defs/` is stale until a manual `generate:defs` run.

### 4. Branch switch (same as codegen-staleness)

`dist/defs/` is gitignored, so old files persist across branch switches.

---

## Risk assessment

**Severity: Low to medium.** Unlike the `__generated__/` staleness (which can cause build failures and runtime crashes), stale Monaco defs cause **incorrect intellisense only** — the app still builds and runs correctly. The user sees wrong autocomplete or missing type info in the DSL editors, but executed code uses runtime values, not the `.d.ts` declarations.

**Frequency: Low.** The defs source files (`src/defs/*.ts`) change rarely — they're stable DSL contracts. SDK type changes that surface through them are also infrequent.

**Mitigation already in place:**
- `start:gen` exists as the "regenerate everything" dev command
- Production builds (`build.sh`) always run `generate:defs`
- The `defs.config.mjs` and `dsl-register-fe.ts` (stages 2 and 5) are now kept fresh by `generate-entries` in `prebuild:be`

## Recommendations

### Option A: Wire `generate:defs` into `prebuild:be`

```diff
- "prebuild:be": "npm run generate:entries -w @app/default-setup && npm run compile",
+ "prebuild:be": "npm run generate:entries -w @app/default-setup && npm run generate:defs -w @app/default-setup && npm run compile",
```

**Pro:** Zero staleness — every `npm start` regenerates defs.
**Con:** Adds rollup bundling time to every start. The rollup step invokes `rollup-plugin-dts` which runs a partial TypeScript compilation — heavier than the pure I/O of `generate-entries`. Needs benchmarking.

### Option B: Keep current split, document the workflow

`npm start` for fast iteration (defs assumed fresh). `npm run start:gen` when defs might be stale (after SDK changes, branch switches, defs edits). Production builds always regenerate.

**Pro:** No added cost to the hot path. Most dev sessions never change defs.
**Con:** Requires developer awareness. Stale intellisense can be confusing.

### Option C: Vite plugin for dev-time defs (Phase 3 territory)

A Vite plugin could intercept `?raw` imports of `*-defs.d.ts` and run rollup-plugin-dts on the fly, producing fresh type bundles at dev-server request time. This would eliminate staleness entirely with zero startup cost — defs are generated lazily when the Monaco editor requests them.

**Pro:** Zero staleness, zero startup cost.
**Con:** Significant implementation effort. rollup-plugin-dts is not trivially callable as a Vite transform — it needs a full rollup pipeline.
